# 케어릿 디자인·UI/UX 실무 기준

확인일: 2026-11-08 (한국 시간)  
목적: 케어릿의 화면을 개선할 때 실제 디자인 사례와 공개 지침을 근거로 일관성 있게 설계하고 검증하기 위한 작업 기준. 이 문서는 참고 기준과 출발점이며, 모든 화면에 그대로 적용해야 하는 확정된 제품 규격은 아니다. 웹 문서와 제품 UI는 변경될 수 있으므로 중요한 수정 전에 해당 출처와 현재 목업을 다시 확인한다.

토스의 실제 UX 사례와 케어릿의 일지·리포트 적용 가설은 [토스 UX 사례와 케어릿 적용 기준](TOSS-UX-AND-CAREIT.md)에 별도로 기록한다.

### 홈 소식 배너의 화면 참고

- [Canva 홈 화면 캡처](https://p16-seeyou-sg.ibyteimg.com/tos-alisg-i-2zwwjm3azk-sg/bcd94aa800fc444e9aec4fa06d1500c0~tplv-2zwwjm3azk-image.image): 외부 튜토리얼에 실린 실제 제품 화면 사례. 중앙에 이벤트 제목을 두고 그 아래 행동 버튼을 배치한다. 캡처 시점과 현재 서비스 화면이 같다고 보장할 수 없다.
- 케어릿에는 **양쪽 그래픽과 배경이 이어지고 가운데 제목·행동을 묶는 구성**을 참고한다. 실제 캔바의 이벤트 그래픽·색상은 복사하지 않고, 케어릿의 일지·리포트를 표현한 맞춤 배경 이미지를 별도로 제작했다. 소식 보기와 이용 방법은 각자 별도의 동작으로 유지한다. 모바일은 그림과 문구가 겹치지 않도록 같은 스타일의 별도 구도를 사용한다.

## 케어릿에서 우선할 원칙

1. **기능을 먼저 파악한다.** 화면의 사용자, 주된 작업, 기존 버튼·데이터 흐름을 확인한다. 별도 요청 없이 기능이나 기존 데이터를 없애지 않는다. 목업의 예시와 실제 기능을 구분한다.
2. **눈에 보이는 요소에는 역할이 있어야 한다.** 각 텍스트, 아이콘, 색, 선, 빈 공간이 의미를 전달하거나 읽기·조작을 돕는지 확인한다. 원이 선택 버튼처럼 보이는데 상태 표시라면 텍스트로 바꾸는 방식을 검토한다. 장식적 요소가 사용자 이해를 방해하면 덜어낸다.
3. **익숙한 사용 방식과 명확한 이름을 쓴다.** 버튼의 문구가 실제 동작을 설명해야 한다. 같은 모양과 색이 다른 행동을 뜻하거나 같은 행동이 화면마다 다른 위치에 있지 않은지 확인한다.
4. **참고 사례를 구체적으로 확인한다.** 다른 서비스의 실제 화면 또는 공식 문서에서 무엇을 봤고, 어떤 점을 케어릿에 어떻게 적용할지 구분해 기록한다. 수상 제품이라고 해서 모든 개별 화면이나 픽셀 값이 상을 받은 것으로 말하지 않는다. 마케팅 페이지와 로그인 후 제품 화면도 구분한다.
5. **간결함은 기능 삭제가 아니다.** 매일 쓰는 작업을 먼저, 추가 설명은 적절한 위치에 두되 접근 경로를 없애지 않는다. 안내를 접는다면 다시 찾는 방법이 분명해야 한다.
6. **초록색은 브랜드색으로 유지한다.** 보조색 사용은 가능하다. 색은 브랜드, 행동, 상태나 정보 구분 등 목적을 가지고 사용하고, 색상만으로 정보를 전달하지 않는다.
7. **개인정보 노출을 줄인다.** 홈에서 민감할 수 있는 일지 본문의 노출 범위를 신중히 결정한다. 실존 사용자 데이터를 테스트 예시로 복사하거나 임의 생성하지 않는다.

## 기본 시각 체계: 케어릿의 시작점

아래 값은 현재 목업에서 사용하는 크기와 기존 디자인 변수를 바탕으로 정한 **작업용 출발점**이다. Adobe·Apple 등의 특정 화면을 동일하게 측정한 값이라고 주장하지 않는다. 필요하면 실제 한글·긴 이름·화면 너비를 보고 조정한다. 사용자가 특정 값을 지정하면 그 지시가 우선한다.

| 역할 | 기본값 | 확인할 점 |
|---|---|---|
| 화면 제목 | 24px, 700 | 한 화면의 제목 계층을 분명하게 |
| 주요 섹션 제목 | 20px, 700 | 같은 역할의 섹션에 같은 시각적 무게 |
| 카드·항목 이름 | 16px, 600 | 긴 대상명은 잘림·전체 확인 방법 검토 |
| 상태·날짜·보조 설명 | 14px, 400~600 | 필요한 상태는 읽을 수 있는 대비 유지 |
| 본문 | 14~16px, 400 | 내용 밀도와 가독성에 맞춤 |
| 한글 제목·짧은 UI | 줄높이 약 1.5 | 줄바꿈 시 겹치거나 잘리지 않게 |
| 한글 여러 줄 본문 | 줄높이 약 1.7 | 문장의 길이와 화면 밀도에 따라 조정 |

Adobe Spectrum은 CJK 웹 글자에 기본 줄높이 150%, 긴 본문에 170%를 안내한다. 숫자는 참고 기준이며, 서체와 문맥이 다른 케어릿에서는 시각적으로 확인한다. [Adobe Typography](https://spectrum.adobe.com/foundations/typography/typography-system)

### 간격과 정렬

- 4·8·12·16·20·24·32·40px 등 제한된 단계에서 출발한다. 실제 관계에 맞는 값을 고르며 배수 규칙만 기계적으로 적용하지 않는다.
- 아이콘과 글자, 제목과 설명은 가깝게; 카드 내부 항목은 12~16px; 카드 내부·카드 간 여백은 대략 20~24px; 주요 구역 사이에는 대략 32px을 출발점으로 둔다.
- 관련 있는 컨테이너는 시작점·끝점·간격을 같은 그리드에 맞춘다. 그리드는 열의 경계를 정리하는 도구이지 모든 카드의 폭을 같게 만들라는 규칙이 아니다. 콘텐츠와 사용 목적에 따라 비대칭 비율도 가능하다.
- 작은 화면에서는 필요하면 열을 쌓고, 제목·버튼·긴 텍스트가 잘리거나 겹치지 않는지 확인한다. 최상단에서 보여야 할 정보가 있다면 실제 뷰포트에서 확인한다. 모든 사용자의 화면에 스크롤 없이 전부 들어간다고 보장하지 않는다.

참고: [Adobe Layout spacing](https://spectrum.adobe.com/foundations/layout-and-structure/spacing/layout-spacing), [Atlassian Grid](https://atlassian.design/foundations/grid), [Apple Layout](https://developer.apple.com/design/human-interface-guidelines/layout?changes=lat_3__1_2).

### 색과 상태

- 초록색은 주요 행동과 케어릿의 브랜드 표현을 중심으로 쓴다. 안내, 소식, 위험, 중립 상태에는 문맥에 맞는 보조색을 쓸 수 있다.
- 배경·카드·입력 영역의 층은 중성색과 여백으로 구분하고, 강한 채색은 실제로 우선순위가 높은 요소에만 검토한다.
- ‘작성 전’, ‘임시저장’, ‘완료’, 오류와 비활성은 색만이 아니라 텍스트나 의미가 분명한 형태로 구분한다. 같은 색이 같은 화면에서 서로 모순되는 뜻을 갖지 않도록 한다.
- 라이트·다크 모드, 호버·포커스·비활성 상태를 따로 확인한다. 사용자 지정 색상은 기본 팔레트의 대비 검증 결과를 그대로 적용할 수 없다.

참고: [Adobe Color](https://spectrum.adobe.com/foundations/color/color), [Apple Color](https://developer.apple.com/design/human-interface-guidelines/color).

## 행동과 문구

- **한 요소, 한 행동:** 카드 전체가 클릭되면 내부에 서로 다른 클릭 대상을 중첩하지 않는다. 한 배너에 서로 다른 목적지가 있으면 각각 이름과 초점을 가진 버튼·링크로 분리한다.
- **링크와 버튼:** 이동은 링크, 현재 화면에서 상태를 바꾸거나 팝업을 여는 행동은 버튼을 우선한다. 키보드와 스크린리더로도 이름과 동작을 알 수 있어야 한다.
- **상태:** 저장 중·완료·오류, 선택·비활성, 빈 화면을 실제 데이터와 일치하게 표시한다. 조건이 충족되지 않아 실행할 수 없다면 이유와 다음 행동을 알 수 있게 한다.
- **사용자 표현:** ‘필수/선택’과 행동 문구를 같은 방식으로 쓰고, 설명은 사용자의 결정에 필요한 경우에만 짧고 구체적으로 제공한다. 미정인 결과나 존재하지 않는 공지를 만들어 내지 않는다.
- **실행의 연속성:** 내용 수정 후 저장, 임시저장 복원, 대상 전환, 되돌리기 등 기존 흐름을 검증한다. 화면이 좁아져도 같은 핵심 기능에 도달할 수 있어야 한다.

참고: [Apple Design principles](https://developer.apple.com/design/human-interface-guidelines/design-principles/), [Apple Writing](https://developer.apple.com/design/human-interface-guidelines/writing), [Atlassian Info messages](https://atlassian.design/foundations/content/designing-messages/info-messages/).

## 접근성 검증 기준

WCAG 2.2는 다음 수치를 제시한다. 예외와 적용 범위가 있으므로 개별 성공 기준을 함께 확인한다. 숫자 일부를 통과했다고 전체 WCAG를 준수했다고 단정하지 않는다.

| 항목 | 기준 또는 케어릿 목표 |
|---|---|
| 일반 텍스트 | 대비 4.5:1 이상; 큰 텍스트는 3:1 이상 등의 예외가 있다. WCAG 1.4.3 AA. |
| 색상 외 정보 | 색 외에도 텍스트·형태 등으로 구분. WCAG 1.4.1 A. |
| 클릭 영역 | WCAG 2.5.8 AA는 원칙적으로 24×24 CSS px 이상이며 간격·문장 내 링크 등 예외가 있다. 케어릿의 주요 터치 컨트롤은 44×44 CSS px 이상을 실무 목표로 삼는다. 이는 AA 최소치와 다르며 WCAG 2.5.5 AAA의 44px 기준에는 별도 예외가 있다. |
| 텍스트 확대 | 200%까지 확대해도 내용과 기능이 손실되지 않아야 한다. WCAG 1.4.4 AA. |
| 리플로 | 보통의 세로 스크롤 콘텐츠는 320 CSS px에 해당하는 폭에서 양방향 스크롤 없이 사용 가능해야 한다. 2차원 배치가 필수인 경우 예외가 있다. WCAG 1.4.10 AA. |
| 키보드 | 탭 순서와 포커스가 보이고, 고정 요소가 포커스된 컨트롤을 완전히 가리지 않도록 한다. WCAG 2.4.11은 AA. |
| 드래그 | 드래그가 필수인 경우 등의 예외를 제외하고 드래그 없이 단일 포인터로도 같은 기능을 사용할 수 있도록 한다. WCAG 2.5.7 AA. |

참고: [WCAG 2.2](https://www.w3.org/TR/WCAG22/), [W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [W3C Resize Text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html), [W3C WCAG 2.2 변경점](https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/).

## 수정할 때의 실제 작업 순서

1. **문제 확인:** 사용자가 지적한 화면과 실제 작동 상태를 보고, 중복·가독성·찾기 어려움 등 문제를 구체적으로 적는다.
2. **근거 확인:** 적절한 실제 제품 화면이나 공식 디자인 시스템을 읽는다. 참고한 원칙과 케어릿에 적용할 부분, 다르게 적용할 이유를 구분한다. 외부의 최신 상태가 중요하면 다시 확인한다.
3. **작은 시안:** 텍스트·정렬·여백·색·상태의 역할을 설명할 수 있게 화면에 적용한다. 필요하다면 사용자가 비교할 수 있는 시안을 만든다.
4. **실제 상태 검증:** 빈 데이터, 긴 이름, 작성 전·임시저장·완료, 오류 및 저장 여부를 확인한다. 해당 변경의 버튼과 링크를 끝까지 실행해 확인한다.
5. **다양한 환경 검증:** 데스크톱·작은 화면, 200% 글자 확대, 키보드 포커스, 라이트·다크 모드를 변경에 맞춰 확인한다. 최소 320 CSS px 리플로가 필요한 화면에는 해당 기준과 예외를 적용한다.
6. **보고:** 어떤 참고를 왜 적용했는지, 무엇을 바꿨는지, 어디까지 검증했는지 말한다. 참고 사례를 직접 보지 않았거나 특정 상태를 확인하지 못했다면 구분해서 밝힌다. 수정된 목업과 실제 서비스 반영 여부도 구분한다.
