# IEP 설계·사용성·향후 API 비용 검수

검수일: 2026-09-26. 현재 로컬 목업 소스와 별도 합성 대상 화면을 확인했다. 제품 코드와 기존 사용자 데이터는 변경하지 않았다. AI 호출은 하지 않았으며 실제 API 비용은 발생·측정하지 않았다. 아래 순위는 데이터 일관성, 교사 작업 시간, 향후 비용 노출을 함께 고려한 권고다.

## 중요도순 5개

### 1. 생성 요청의 중복·사용량 제한을 AI 연결 전에 확정해야 한다

**분류: 연결 전 필수 / 비용·대기 UX.** 지금의 즉시 완료되는 예시 생성 자체가 과금 버그라는 뜻은 아니다.

- 근거: `iep.js:262`의 생성에는 진행 중 잠금과 요청 식별자가 없다. `savePlan()`의 중복 저장 방지는 저장 동작에만 적용된다. 기존 비용 검토 문서 `careit-iep-planning/03-COSTS.md`는 검증을 통과해 저장됐을 때 사용량을 차감하는 안을 제시했다.
- 예상 문제: 느린 응답에 연속 클릭하거나 오류 뒤 다시 눌러 같은 생성이 중복 실행될 수 있다. 사용자가 결과를 받고 저장하지 않는 경우를 비용·사용량에서 누락하면 제한이 우회된다. 사용자 한 명의 정상 형식 반복 요청도 서비스 전체 예산을 소모할 수 있다.
- 설계: 생성 중 버튼에 진행 상태를 표시한다. 서버는 사용자·대상·계획·입력 버전과 자료/프롬프트 버전을 묶어 동일 작업을 식별하고 진행 중 요청과 완료 결과를 재사용한다. 다른 계정의 결과를 공유하지 않는다. 타임아웃은 먼저 기존 작업 상태를 조회하며 무조건 새 호출로 바꾸지 않는다. 오래된 응답은 변경된 대상·입력에 덮어쓰지 않는다.
- 비용 규칙: 성공한 생성 작업을 기준으로 이용량을 한 번만 차감한다. 명시적 저장 여부와 분리한다. 실패한 공급자 호출 비용은 회사 내부 원가에는 기록하되 사용자에게 실패 횟수를 자동 차감하지 않는다. 계정별 생성 한도와 서비스 전체 예산을 서버에서 확인·예약하고, 초과 시 새 생성만 중단한다. 직접 수정·저장·내려받기는 계속 허용한다. 구체적인 월 한도는 대상 수와 실측을 보고 정하며 이 검수에서 임의로 확정하지 않는다.
- 완료 기준: 10회 연속 클릭과 두 탭의 동일 요청이 같은 작업으로 합쳐진다. 성공 응답 유실 뒤 재접속은 기존 결과를 반환한다. 실패·재시도·입력 변경·대상 전환을 구분하며, 예산 잔액을 동시에 초과 예약하지 않는다. API 키와 한도 검사는 브라우저에 두지 않는다.

Gemini의 공급자 제한은 프로젝트 기준이며, 케어릿 사용자별 이용 규칙을 대신하지 않는다. [공식 rate limits](https://ai.google.dev/gemini-api/docs/rate-limits). Google Cloud도 알림 전용 예산과 실제 지출 제한 예산을 구분하므로 연결 시 지원 범위와 설정을 확인한다. [공식 예산 문서](https://docs.cloud.google.com/billing/docs/how-to/budgets).

### 2. 입력 수정과 AI 생성을 분리하고, 목표가 바뀐 기존 내용을 표시해야 한다

**분류: 현재 브라우저 재현 + 연결 전 비용 예방 / 높은 우선순위.**

- 근거: `iep.js:274`는 입력 변경 유무에 관계없이 전체 결과를 다시 구성한다. `iep.js:280`부터 교사가 편집한 결과 항목과 실제 관찰을 그대로 보존한다. 결과 본문의 월 목표를 직접 수정하는 경로도 관련 활동·평가 문장과의 일관성을 검사하지 않는다.
- 재현: 저장 계획의 월 목표를 도움 요청에서 친구와 번갈아 블록 쌓기로 변경했다. 활동·평가계획은 친구 놀이로 바뀌었으나, 직접 편집한 자동차 도움 요청 지원과 자동차 놀이 관찰 결과는 새 목표 아래 그대로 남았다. 화면은 일반적인 수정 중 상태만 표시했다.
- 예상 비용: 현재의 전체 결과 구성 자리를 그대로 API 호출로 바꾸면 오탈자 수정이나 바뀐 내용 없는 제출에도 비용과 대기 시간이 생긴다.
- 설계: 변경 내용 반영과 직접 편집·저장은 기본적으로 API를 호출하지 않는다. 같은 입력이면 기존 결과로 돌아간다. 목표·현행수준 등 핵심 내용이 바뀌면 관련 활동·지원·평가에 짧은 재검토 표시를 붙인다. 교사 수정값을 자동 삭제하지 않는다. 목표가 달라졌을 때 이전 실제 관찰은 원래 목표·버전에 묶어 보존하고 새 목표의 결과처럼 섞지 않는다. 새 목표를 별도 계획으로 만들지 기존 계획을 수정할지 명확히 구분한다. 재생성 버튼을 추가하는 것은 이번 권고에 포함하지 않는다.
- 완료 기준: 입력 수정·저장·보기·다운로드의 모델 호출은 0회다. 목표 변경 후 관련 항목과 이전 관찰의 소속이 드러난다. 단순 문구 수정과 목표 자체 변경을 사용자 확인 없이 AI가 임의 판정해 기록을 이동하지 않는다.

### 3. AI가 작성할 범위와 한 요청의 분량을 제한해야 한다

**분류: 연결 전 필수 / 반복 원가·응답 시간.**

- 근거: 현재는 계획 입력을 허용된 필드만 추리는 `planningInput()`이 있어 불필요한 대상 정보·일지 원문을 제외하고 있다. 입력칸은 각 1,200자 제한이 있지만, 이는 향후 서버의 토큰 제한이나 AI 출력 제한이 아니다. 결과에는 교사의 원문, 반복되는 목표 문장, 안내성 내용이 함께 있다.
- 추가 확인: 과거 비용 계산은 생성 1회 + 검증 1회, 가정한 자동 보완 10%, 월 계획 + 주 계획을 포함한다. 현재 월간 전용 설계와 다르므로 그 금액을 현재 1명당 월 비용으로 그대로 사용하면 안 된다.
- 설계: 교사가 쓴 1~2번은 코드가 원문을 넣고, AI는 3~6번의 필요한 제안만 구조화된 내용으로 반환하게 한다. 실제 관찰 결과는 생성하지 않는다. 제목·표·HTML·PDF는 코드가 만들고, 다음 계획의 기본 조건문도 매번 AI로 다시 쓰지 않는다. 자료는 이번 목표와 관련된 고시 부분과 자체 규칙으로 범위를 정한다. 기본 요청에 실시간 검색·전체 문서·모든 과거 일지·대화 누적을 넣지 않는다.
- 비용 규칙: 입력 총토큰, 출력 길이, 모델별 생각 설정과 도구 사용 범위를 서버에서 정한다. 날짜·필수값·형식은 코드로 검사한다. 별도 모델 검증의 필요성은 품질 시험으로 정하고, 생성→검증→수정이 무한 반복되지 않게 작업 전체의 최대 호출·비용을 제한한다. 중요한 안전 지원 문장은 조용히 잘라내지 않는다.
- 완료 기준: 선택한 생성 단위의 실제 호출 수와 입력·출력·생각·추가 도구 비용을 측정한다. 길이 제한으로 잘린 결과를 완료 처리하거나 자동 반복 생성하지 않는다. 직접 작성한 내용이 AI에 의해 바뀌지 않는다. 긴 입력과 여러 목표를 넣은 경우에도 분량·처리 범위가 예측 가능해야 한다.

생각 토큰과 일부 도구 사용도 비용에 영향을 준다. [Gemini 공식 가격표](https://ai.google.dev/gemini-api/docs/pricing). 출력 한도를 지나치게 줄이면 빈 결과나 잘린 결과가 반환될 수 있으므로 분량 제한과 품질 확인을 함께 해야 한다. [공식 thinking 문서](https://ai.google.dev/gemini-api/docs/generate-content/thinking).

### 4. 결과 검토 화면이 길고 계획 작성과 실행 후 기록이 섞여 있다

**분류: 현재 화면 확인 / UX 높은 우선순위.**

- 근거: `renderResult()`는 7개 섹션·20개 편집칸을 모두 펼친다. 테스트 브라우저의 화면 높이 720px에서 문서 높이는 4,268px로 약 6화면이다. 빈 선택 정보도 입력칸으로 노출된다. 저장 동작은 본문 맨 아래에 있다. 분량은 입력과 화면 크기에 따라 달라진다.
- 문제: 교사가 검토할 핵심 활동·지원·평가를 찾기 어렵고, 이미 입력한 현행수준·목표를 다시 검토하며 아래까지 이동해야 한다. 계획을 만드는 시점과 실제 관찰을 적는 시점이 같은 길이의 편집 화면에 섞인다. 읽기 부담 때문에 다시 만들기를 찾게 되더라도, 이는 확인된 사용자 행동이 아니라 예상 UX 위험이다.
- 설계: 공식 문서의 항목 구조는 유지하면서 화면은 활동·교사 지원·평가초점을 중심으로 보여 준다. 현행수준·목표, 빈 선택 정보, 세부 준비 항목은 짧은 요약과 펼치기로 접근하게 한다. 실제 관찰·다음 달 검토는 실행 후 기록 영역으로 분리하고 바로 수정할 수 있게 한다. 저장 버튼과 수정 상태는 긴 스크롤에서도 접근 가능하게 한다. 예전처럼 번호별 메뉴나 설명 문장을 여러 개 추가하지 않는다.
- 완료 기준: 390px와 데스크톱에서 핵심 계획·직접 수정·저장을 찾을 수 있다. 펼침 동작은 API를 호출하지 않는다. 긴 텍스트와 키보드 이동에서도 필드·오류를 숨기지 않고 모든 내용은 계획서에 유지한다.

### 5. 다음 달 계획을 이어 쓰는 흐름이 없어 불필요한 신규 작성이 생긴다

**분류: 현재 동선·코드 확인 / UX·장기 호출량.**

- 근거: 저장 목록은 계획 보기만 제공한다. 새 계획은 빈 초안을 만들고 기간은 목업 고정 2026년 9월로 돌아간다. 지난 계획을 별도 초안으로 복사하는 기능은 없다. 새로운 ID로 저장하면 같은 대상·기간의 별도 계획이 만들어진다.
- 문제: 같은 목표를 다음 달에도 이어갈 때 사용자는 다시 입력하거나 이전 저장본의 날짜를 바꾸게 된다. 전자는 나중에 새 AI 생성으로 이어질 수 있고, 후자는 지난달 기록을 수정할 우려가 있다. 여러 교육목표를 동시에 운영하는 정상 사용까지 월 1개로 막아서는 안 된다.
- 설계: 저장한 계획에서 다음 달 계획으로 복사할 수 있게 한다. 새 ID와 새 기간을 만들고 원본은 유지한다. 목표·활동·지원을 가져오되 실제 관찰 결과와 검토 완료 상태는 새 계획에 이월하지 않는다. 같은 대상·기간·목표의 계획이 있으면 먼저 이어쓰기 동선을 제공하고, 별도 목표 계획은 허용한다. 복사와 날짜 조정 자체는 AI 호출 없이 처리한다.
- 완료 기준: 9월 계획을 10월 초안으로 복사해도 9월 원본·관찰은 그대로 남는다. 새 초안은 미검토·관찰 공란이고 호출은 0회다. 월말·윤년 기간 계산, 기존 작성 초안 보존, 서로 다른 목표의 병행 계획을 확인한다.

## 비용 산정과 검수 범위

향후 비용은 새로 만든 월간 계획 수에 각 생성 작업의 입력·출력·생각·추가 호출 비용을 더해 계산한다. 보기·직접 수정·저장·복사·내려받기는 AI 비용이 없어야 한다. 대상 수만으로 금액을 고정하지 않고, 한 대상의 복수 목표와 실제 생성 작업 수를 구분한다. 이번에는 단가나 절감률을 실측한 것처럼 제시하지 않는다.

API 대기·429·타임아웃·중복 요청·늦은 응답·한도 초과는 현재 목업에 지연된 가짜 응답과 호출 카운터를 넣어 UX를 검수할 수 있다. 실제 공급자 재시도·청구·서버 권한·한도 예약의 정확성은 AI 연결 후 검수해야 하며 목업만으로 통과 판정을 내리지 않는다.

브라우저 재현은 `_qa/iep-design-cost-20260926.html`의 합성 대상에서 진행했다. 증거 이미지: `_qa/iep-design-goal-mismatch.png`. 제품 코드 수정과 API 연결은 이번 검수에 포함하지 않는다.
